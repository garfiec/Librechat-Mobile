For server admins

Set up your server for Switchboard

Switchboard works with any standard LibreChat server. A few settings make it work smoothly for everyone on yours.

Recommended: one line in .env

NON_BROWSER_VIOLATION_SCORE=0

The app identifies itself like a browser, but if that check ever fails, LibreChat adds ban points against the account. Without this setting, a single misread request can lock an account out for two hours.

Sign-in behind Authelia

When your server sits behind an Authelia forward-auth gate, the app recognises the gate when someone connects and offers Sign in with Authelia. They sign in on Authelia's own pages in the system browser (password, two-factor, passkeys and password managers all work), then to LibreChat as usual. Without the setup below, the app falls back to Authelia's page inside the app, where passkeys don't work and the session lasts only as long as Authelia's cookie.

You need Authelia 4.38 or later. Register a public client for the app. The client_id can be anything (users enter a name other than switchboard under Advanced); the redirect URI must be exactly http://127.0.0.1/callback:

identity_providers:
  oidc:
    clients:
      - client_id: 'switchboard'
        client_name: 'Switchboard'
        public: true
        authorization_policy: 'two_factor'
        require_pkce: true
        pkce_challenge_method: 'S256'
        require_pushed_authorization_requests: true
        redirect_uris:
          - 'http://127.0.0.1/callback'
        scopes: ['offline_access', 'authelia.bearer.authz']
        audience: ['https://chat.example.com']
        grant_types: ['authorization_code', 'refresh_token']
        response_types: ['code']
        response_modes: ['form_post']
        consent_mode: 'explicit'
        token_endpoint_auth_method: 'none'

LibreChat uses the Authorization header for its own sign-in, so the app sends Authelia's token as Proxy-Authorization. Let the authz endpoint read it, and keep the cookie strategy for browsers:

server:
  endpoints:
    authz:
      forward-auth:
        implementation: 'ForwardAuth'
        authn_strategies:
          - name: 'HeaderProxyAuthorization'
            schemes: ['Bearer']
          - name: 'CookieSession'

Your reverse proxy must pass Proxy-Authorization on to Authelia. Caddy drops it unless told otherwise:

forward_auth authelia:9091 {
	uri /api/authz/forward-auth
	header_up Proxy-Authorization {http.request.header.Proxy-Authorization}
	copy_headers Remote-User Remote-Groups Remote-Email Remote-Name
}

Refresh tokens last 90 minutes by default, so a phone left alone longer has to sign in to Authelia again. To keep users signed in longer, give the client longer lifespans (identity_providers.oidc.lifespans.custom, then lifespan: on the client), for example 30 days for refresh tokens.

Cloudflare Access and other header-based gateways

For a gateway that lets requests through on fixed headers, such as a Cloudflare Access service token, users add the headers when they connect: under Advanced on the server address screen, or later in Settings → Advanced → Server connection. For Cloudflare Access, create a service token and give them its CF-Access-Client-Id and CF-Access-Client-Secret.

Self-signed TLS certificates

Both platforms trust a private certificate authority once it's installed on the device, but they check certificates more strictly than browsers do. A certificate that works in Chrome or Safari can still be refused by the app. It needs:

  • The server's DNS name in the Subject Alternative Name (the CommonName alone is ignored).
  • A SHA-256 or stronger signature, and an RSA key of at least 2048 bits or a modern ECDSA curve.
  • Extended Key Usage with TLS Web Server Authentication on the leaf, and CA:TRUE on the issuing CA.
  • On iPhone and iPad, a leaf certificate valid for 825 days or less.

mkcert makes certificates that meet all of these. Then each user installs your CA certificate on their phone:

  • iPhone and iPad: Settings → General → VPN & Device Management to install it, then Settings → General → About → Certificate Trust Settings to turn on full trust.
  • Android: Settings → Security → Encryption & credentials → Install a certificate → CA certificate (search Settings for "CA certificate" if it's elsewhere).

If users can't install a CA (a managed phone, for example), use a publicly trusted certificate such as Let's Encrypt, or a reverse proxy that serves one. Plain http:// works on Android with a warning, and on iPhone only to a local address (a local IP, a .local name or a single-word name like http://nas). The full guide has the details.

Running LibreChat under a subpath

Users enter the full address, path included, for example https://example.com/librechat. The app keeps the path for every request.

Registration

The app follows your server's registration settings. If registration is off, users only see the sign-in form.
